# `std` 待办：包身份、发布卫生与能力缺口

> **历史文档**：本文的“下一步”清单已被 [roadmap](roadmap.md) 取代；保留作证据，不再更新。

| 项 | 值 |
| --- | --- |
| 性质 | 待办台账：只登记与验收，不改 `ct.pkg`、不动版本号、不打 tag |
| 基线 | `0.3.1`；默认分支 `main` |
| 日期 | 2026-11-15 |

## 1. 发布机制现状（本仓核实）

过去这里把「包管理器能读到发布者、能把命名空间根接进 include、能默认读 lock」当作待等的能力。
按实际情况核过：这些机制已经存在，**不再是阻塞**。本仓能确认的事实：

- 包的 store 按发布者 / 包名 / 版本落盘；`publisher` 与 `ns-root` 是必填项，后者参与 include 根展开。
- lock 记录发布者与单元根；构建默认读取 lock，并自动补 include 根。
- 索引条目含 `name`、`version`、`publisher`、`url`、`tag`、`sha` 六个字段。

本仓实测（只读验证，无改动）：

- `ct` 提供 `get` / `install` / `build` / `check` 子命令，**没有** `pkg check`；`ct pkg check .` 会把
  `check` 当作第二个输入而报错。因此旧验收命令不可用，需要换一种验收方式。
- `ct build --ns-root . tests/fs/main.ct` 无法解析现有 `import std/fs/Fs`；加上 `-I .` 后构建成功，
  并自动追加了 `-I './std/fs'`、`-I './std/str'` 等根。`--ns-root` 与当前目录布局的配合方式仍需确认，
  但这不构成「能力未具备」。

结论：本仓的待办里，**没有一项还在等发布机制**。真正的阻塞只有两类：本仓还没做的实现工作，
以及语言层尚未提供的能力（仅影响 `result` / `callback`）。

## 2. 待办逐项

### 2.1 包身份声明与验收

**为什么**：消费方需要区分同名包，并让 `import std::<mod>::<Unit>` 按包声明的命名空间根解析。

**现状（2026-11-19 更新）**：官方身份已归一为 `publisher = ct`（规范名 `ct/std`），`ns-root = .` 不变；见 `ct.pkg`。

**真实缺口**：缺一条本仓可执行的验收——没有 `pkg check` 可用，且尚未做一次「从索引安装本包再构建」
的闭环；`--ns-root` 的正确用法也待确认（见 §1 实测）。

**能否立即开工**：**能**，属验证工作：用 `ct get` / `ct install` 走一次真实安装，再用 `ct build`
构建一个只依赖包名、不手写 `-I` 的样例。验收通过后本项关闭。

### 2.2 tag 必须落在默认分支历史内

**为什么**：游离 tag 会让「按 tag 复现」拿到分支上不存在的树。

**现状**：`v0.2.0` 已满足（`git merge-base --is-ancestor v0.2.0 main` 为 0）。

**能否立即开工**：无工作可做，已完成；后续每次发布前跑同一检查。

### 2.3 依赖写法：全名 + 版本范围

**为什么**：裸包名在多个发布者共存时无法定位。

**现状**：本仓当前没有任何包依赖；`ct.pkg:43` 的 `requires = ct >= 0.30.0` 是编译器下限，不是包依赖。

**能否立即开工**：**暂时没有对象**。首个包依赖出现时按 `<publisher>/<name>@<range>` 写，并在依赖图内
保证包名唯一。

### 2.4 应用层能力缺口

四项都不再被外部能力阻塞，只差本仓实现与排期。

| 子项 | 为什么需要 | 做什么 | 验收 | 现状 |
| --- | --- | --- | --- | --- |
| 文件属性查询 | 调用方要大小/权限/时间，又不想为 `stat` 的结构体布局建模 | `file_size()` / `file_mode()` / `file_mtime()` | 三个值各有 fixture；文档写明每次一次 `stat` | 方案已定（[设计提案 §2.5](design/std-scope-and-presentation.md)），未实现 |
| 字符串增量 | 反向查找、忽略大小写比较、带错误报告的数值解析现在要么手写、要么无法区分失败 | `rfind_char`、`compare_ignore_case`、`parse_long` / `parse_llong` / `parse_ulong` / `parse_real` | `tests/str/` 覆盖未命中与非法输入；`tests/run.sh` 全绿 | 方案已定（[issue 0001](../issues/0001-str-string-trait-rename.md)），未实现 |
| 原子写 | 现有 `write_file` 是整文件替换（`std/fs/README.md:10`），中途失败会留下半截文件 | 评估 `write_file_atomic`：同目录临时文件 + 写入 + `rename` | 失败场景留下旧文件或完整新文件；fixture 断言 | `rename` 已有；原子路径未实现 |
| UTF-8 显示宽度 | `count_codepoints()` 只数码点，终端列宽算不出来 | 评估 `count_columns`：按码点区间判定宽度 | 全角、组合符、emoji 各有用例 | 未实现；现仅 `decode` / `count_codepoints` / `encode` |

`Map` / `Vec` 不在本表：它们是内置层，本包只调用。

### 2.5 是否新建上层包

| 候选 | 结论 | 真实理由 |
| --- | --- | --- |
| `arena` | 不新建 | `std::arena` 已有 `Arena` + `ArenaOps` |
| `string` | 不新建 | `std::str` 覆盖借用层（拟改 `CStrOps`），拥有型字符串由语言侧内置 `Str` 提供；再建包会出现第三套写法 |
| `sync` | 不做 | 并发/同步属语言与运行时能力，不在本包边界 |
| `result` | 阻塞在语言能力 | 需要语言级「可判错的结果/联合类型」；本包无法自造可靠的错误联合体 |
| `callback` | 阻塞在语言能力 | 需要语言级函数指针/回调能力；契约应由语言层定义，本包不预设签名 |

**能否立即开工**：`arena`、`string`、`sync` 已关闭；`result`、`callback` 不可开工，等语言能力，
本仓不排任何前置任务。

## 3. 进度与分期（本仓自定）

只有「跨多次提交、有明确验收门槛、彼此有先后依赖」才立 phase；其余是检查清单项或触发式任务。

| 事项 | 完成度 | 本仓分期判断 | 下一步 |
| --- | --- | --- | --- |
| 2.1 包身份验收 | 声明完成，验收未做 | 一次安装闭环验证，不立 phase | 先走 `ct get` / `ct install` 真装一次 |
| 2.2 tag 卫生 | 已完成 | 不立 phase | 发布前检查一次 |
| 2.3 依赖写法 | 规则成立，无对象 | 不立 phase，触发式 | 首个依赖出现时适用 |
| 2.4 属性查询 + 字符串增量 | 方案已定，未实现 | 合并为一个 phase | **本仓下一步首选** |
| 2.4 原子写 | 未开始 | 单独一个 phase | 先出半页设计 |
| 2.4 UTF-8 宽度 | 未开始 | 暂不立 phase | 有真实调用点再评估 |
| 2.5 五个上层包 | 结论已定 | 不立 phase | 每版复核一次 |

**本仓判断**：机制层面没有阻塞；七项里 1 项已完成（tag），1 项可立即验证（包身份），1 项无对象
（依赖写法），2 项可立即实现（属性查询、字符串增量），1 项需先设计（原子写），1 项观察（宽度），
2 项冻结（`result` / `callback`）。

**先后顺序**：① 属性查询（最小、独立）→ ② 字符串增量（同属接口补齐，验收同为 fixture）→
③ 包身份安装验收（验证动作，可与 ① 并行）→ ④ 原子写设计 → ⑤ 宽度与上层包维持观察。

## 4. 本仓实际状态

**已具备**

- `publisher` / `ns-root` 已声明，且发布机制支持它们。
- `v0.2.0` 在默认分支历史内。
- `Fs.rename`、`path.exists`、文件属性查询有明确落地路径。

**缺**

- 包身份的真实安装闭环与 `--ns-root` 正确用法。
- 属性查询、字符串增量、原子写、UTF-8 宽度四项实现。
- 无任何包依赖（依赖写法规则暂无对象）。

**工作区**

| 文件 | 现状 | 建议 |
| --- | --- | --- |
| `ct.pkg` | 无未提交改动 | 保持不动 |
| `issues/0001-path-file-traits.md` | 有 1 处未提交改动：样例命令改为 `ct build -I .` | 与本台账无关，未提交也未丢弃；由 owner 决定处置 |

## 5. 需要 owner 拍板

1. 是否按 §3 的顺序开工：属性查询 → 字符串增量 → 原子写设计。
2. 包身份验收是否用「从索引安装后构建」替代已不可用的 `pkg check`。
3. `result` / `callback` 是否维持冻结，等语言能力。
4. `issues/0001-path-file-traits.md` 的未提交改动由谁处置。

## 6. 执行纪律

- 只在本仓推进与验收；文档只写本仓语境，不引用外部册子的编号、来源或阶段号。
- 不动 `ct.pkg` 的身份字段，不动版本号，不打 tag，除非有明确的发布决定。
- `Vec`、`Map` 属内置层：本包**只调用，不泛化、不补齐**，也不把这类缺口转成别处的任务；本仓
  不为它们排任何工作。
